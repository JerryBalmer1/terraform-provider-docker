# terraform-provider-docker

The `JerryBalmer1/docker` provider drives the Docker Engine API directly. It
owns the whole chain from image to Swarm workload. **No compose YAML at
runtime**: the provider never shells out to the `docker` CLI, and you must not
generate `docker-compose.yml`, `docker stack deploy` calls or `local-exec`
provisioners that run `docker`. Express every compose concept as a resource
(see "Translating compose" below). An existing compose file is converted once
into HCL with `go run ./tools/compose2stack` (worked example 2); after that the
generated `.tf` is the source of truth.

This build registers 15 resources, 15 data sources,
13 actions, 3 ephemeral resources, 8 list resources
and 4 provider functions. Per-type argument tables are in
[reference/](reference/) and are generated from the provider schema, so they are
authoritative over anything written here.

```terraform
terraform {
  required_providers {
    docker = {
      source = "JerryBalmer1/docker"
    }
  }
}

provider "docker" {
  host = "tcp://10.0.0.10:2376" # or DOCKER_HOST; default unix:///var/run/docker.sock
}
```

The provider block points at ONE daemon. For Swarm that daemon must be the
manager: services, secrets, configs, overlay networks and node updates all go
through it. Worker hosts are reached only by `docker_swarm_node.host`, which is
used to make that host join.

## 2. Dependency order

Terraform orders by references. Prefer references (`docker_x.y.id`) over
`depends_on`; add `depends_on` only where the dependency is real but no
attribute carries it.

1. `docker_image` before anything that runs it. `docker_registry_image` after
   `docker_image` (it pushes the local tag, so reference
   `docker_image.x.name` or add `depends_on`). Swarm workers pull images
   themselves, so a locally built image must be pushed to a registry the
   workers can reach before a `docker_service` uses it.
2. `docker_swarm_init` before every Swarm object. Overlay networks, secrets,
   configs and services fail with "This node is not a swarm manager" when
   created first. A plain `docker_network` with `driver = "overlay"` has no
   attribute pointing at the swarm, so give it
   `depends_on = [docker_swarm_init.this]`; do the same for `docker_secret`
   and `docker_config` when nothing else orders them.
3. `docker_swarm_node` after `docker_swarm_init`, using its tokens:
   `join_token = docker_swarm_init.this.worker_join_token` (or
   `manager_join_token` with `role = "manager"`) and
   `manager_address = "<manager ip>:2377"`. The token reference already orders
   the join after init.
4. `docker_secret` and `docker_config` before the `docker_service` that mounts
   them; reference `docker_secret.x.id` in the service's `secrets` block and the
   order follows.
5. `docker_service` after the networks it attaches to (reference
   `docker_network.x.id` in `networks`) and, when placement constraints need
   workers, `depends_on = [docker_swarm_node.a, docker_swarm_node.b]`; otherwise
   tasks sit pending until workers join and `converge_config` times out.
6. Destroy runs in reverse: services, then secrets/configs/networks, then
   nodes leave, then the manager leaves the swarm. Do not break the reverse
   chain with `-target` on a lower layer while upper layers still exist.

Gotchas to plan around:

- **Secrets and configs are immutable** in Swarm. Changing `data` or `name`
  replaces them, and a secret in use by a service cannot be removed. Rotate by
  putting a version suffix in `name` (`db_password_v2`) together with
  `lifecycle { create_before_destroy = true }`, so the new secret exists, the
  service updates to it, and only then the old one is deleted.
- **Networks are immutable**: driver, IPAM, `internal`, `attachable`, options
  cannot change in place. A replaced network detaches running containers and
  service tasks; expect a service update.
- **Image triggers**: `docker_image` and `docker_registry_image` re-pull,
  rebuild or re-push only when an attribute or a `triggers` map value changes.
  Put a content hash in `triggers` (for example
  `sha1(join("", [for f in fileset(path.module, "app/**") : filesha1("${path.module}/${f}")]))`)
  to rebuild when the build context changes. Pin services to
  `docker_image.x.repo_digest` so a new pull of the same tag rolls the service.
- **`docker_swarm_init` destroy = leave the swarm.** Destroying or replacing it
  makes the manager leave and tears down every Swarm object with it. Changing
  `advertise_addr` or `listen_addr` therefore rebuilds the whole cluster; guard
  it with `lifecycle { prevent_destroy = true }` in long-lived environments.
- **`docker_swarm_node` replacement = leave and rejoin.** Changing the joining
  `host`, `join_token` or `manager_address` makes the node leave and join again
  with a new node ID; `availability`, `role` and `labels` update in place.
- Containers are replaced on most changes; use services for rolling updates.

## 4. Write-only arguments (`*_wo`)

Terraform >= 1.11. A write-only argument is sent to the provider on create and
update but its value is **never stored in state or shown in plan** (it reads
back as null). Use one for every secret you would otherwise put in a normal
argument (registry passwords, secret data). They come in pairs:

- `<name>_wo`: the write-only value. It may be an ephemeral value (an
  `ephemeral` resource attribute or an `ephemeral = true` variable), which a
  normal argument cannot accept.
- `<name>_wo_version`: a normal (stored) number or string. Terraform cannot
  diff a value it never stores, so the provider only re-sends `<name>_wo` when
  this changes. Bump it to rotate the value; changing only `<name>_wo` does
  nothing.

Set either `<name>` or `<name>_wo`, never both. Older
Terraform (< 1.11) rejects write-only arguments outright, so pin
`required_version = ">= 1.11"` when you use them.

| Resource | Write-only argument | Description |
|---|---|---|
| `docker_config` | `data_wo` | Config content as a write-only argument (Terraform 1.11+), base64-encoded (use `base64encode()`); it is never stored in plan or state, so it can come from an ephemeral value. |
| `docker_secret` | `data_wo` | Secret content as a write-only argument (Terraform 1.11+), base64-encoded (use `base64encode()`); it is never stored in plan or state, so it can come from an ephemeral value. |
| `docker_swarm_node` | `ssh.password_wo` | SSH password, write-only variant of `password`. |

## 5. Actions

Terraform >= 1.14. An action is an imperative operation (run a command in a
container, scale a service, prune, export) that Terraform runs but does not
track in state. Use one when the effect is a one-off step around a resource's
lifecycle, not an object whose existence Terraform should manage: seeding a
database after it is created, a migration after an image update, scaling a
service for a load test without changing the configured `replicas`. If you
want Terraform to keep converging a value, use a resource argument instead
(an action that sets replicas is overwritten by the next apply of a
`docker_service` that manages `replicas`).

Registered in this build:

- [`action.docker_container_export`](reference/action.docker_container_export.md): Writes a container's filesystem to a local tar file, like `docker export`.
- [`action.docker_exec`](reference/action.docker_exec.md): Runs a command inside a running container, like `docker exec`, and fails when it exits non-zero.
- [`action.docker_image_import`](reference/action.docker_image_import.md): Creates an image from a filesystem tarball, like `docker import`.
- [`action.docker_image_load`](reference/action.docker_image_load.md): Loads images from a local tar archive into the daemon, like `docker load`.
- [`action.docker_image_prune`](reference/action.docker_image_prune.md): Removes unused images, like `docker image prune`, and reports the space reclaimed.
- [`action.docker_image_save`](reference/action.docker_image_save.md): Writes one or more images to a local tar archive, like `docker save`.
- [`action.docker_node_activate`](reference/action.docker_node_activate.md): Sets a swarm node's availability back to `active`, like `docker node update --availability active`.
- [`action.docker_node_drain`](reference/action.docker_node_drain.md): Sets a swarm node's availability to `drain` and waits until its tasks have left, like `docker node update --availability drain`.
- [`action.docker_service_force_update`](reference/action.docker_service_force_update.md): Redeploys every task of a swarm service without changing its spec, like `docker service update --force`.
- [`action.docker_service_rollback`](reference/action.docker_service_rollback.md): Rolls a swarm service back to its previous spec, like `docker service rollback`, and waits for the rollback to complete.
- [`action.docker_service_scale`](reference/action.docker_service_scale.md): Sets the replica count of a replicated swarm service, like `docker service scale`, and waits for the tasks.
- [`action.docker_swarm_rotate_tokens`](reference/action.docker_swarm_rotate_tokens.md): Rotates the swarm join tokens, like `docker swarm join-token --rotate`.
- [`action.docker_system_prune`](reference/action.docker_system_prune.md): Removes unused Docker objects, like `docker system prune`, and reports the space reclaimed.

Declare an action with its arguments in a `config` block, then either trigger
it from a resource's lifecycle or invoke it by hand:

```terraform
action "docker_exec" "migrate" {
  config {
    # arguments from reference/action.docker_exec.md
  }
}

resource "docker_service" "api" {
  # ...

  lifecycle {
    action_trigger {
      events  = [after_create, after_update] # before_create, after_create, before_update, after_update
      actions = [action.docker_exec.migrate]
      # condition = <bool expression> # optional
    }
  }
}
```

```shell
terraform apply -invoke=action.docker_exec.migrate   # run just this action now, nothing else changes
terraform plan  -invoke=action.docker_exec.migrate   # preview it
```

Actions that fail fail the apply. They run against the daemon of the provider
configuration they use (alias with `provider = docker.<alias>` inside the
`action` block).

## 6. Ephemeral resources

Terraform >= 1.10. An `ephemeral "<type>" "<name>"` block is opened on every
plan and apply and its values are **never persisted** in plan or state. Its
attributes may only be referenced from ephemeral contexts: write-only
arguments (`*_wo`), `provider` blocks, other ephemeral resources, and
variables, locals and outputs marked `ephemeral = true`. Referencing one from a
normal resource argument is an error. Typical use: fetch a credential and feed
it to a `*_wo` argument or to a provider block, so it never lands in state.

Registered in this build:

- [`ephemeral.docker_exec_output`](reference/ephemeral.docker_exec_output.md): Runs a command in a running container (`docker exec`) and returns its standard output as an ephemeral value that is never written to plan or state.
- [`ephemeral.docker_registry_token`](reference/ephemeral.docker_registry_token.md): Obtains a short-lived registry bearer token, as an ephemeral value that is never written to plan or state.
- [`ephemeral.docker_swarm_tokens`](reference/ephemeral.docker_swarm_tokens.md): Reads the worker and manager join tokens of the swarm the provider's Docker host manages, as ephemeral values that are never written to plan or state.

## 7. Provider functions

Terraform >= 1.8. Pure functions called as `provider::docker::<name>(...)`;
the module must declare the provider in `required_providers`. They run at plan
time without touching the daemon, so use them for parsing and formatting (for
example image references), never for lookups.

| Function | Signature | Summary |
|---|---|---|
| [`compose_env`](reference/function.compose_env.md) | `provider::docker::compose_env(env map(string)) list(string)` | Turns a map of environment variables into a list of `KEY=VALUE` strings sorted by key, the form of env files, compose `environment` lists and the Engine API `Env` field. |
| [`image_ref`](reference/function.image_ref.md) | `provider::docker::image_ref(registry string, repository string, tag string, digest string) string` | Builds a fully qualified image reference such as `docker.io/library/nginx:1.27@sha256:...` from its parts, validating each one. |
| [`parse_image_ref`](reference/function.parse_image_ref.md) | `provider::docker::parse_image_ref(ref string) object({digest=string, registry=string, repository=string, tag=string})` | Splits an image reference into `registry`, `repository`, `tag` and `digest`, normalized like the docker CLI. |
| [`port_spec`](reference/function.port_spec.md) | `provider::docker::port_spec(spec string) object({container_port=string, host_ip=string, host_port=string, protocol=string})` | Parses a `docker run -p` port spec, `[host_ip:][host_port:]container_port[/protocol]`, into `host_ip`, `host_port`, `container_port` and `protocol`. |

## 9. Worked example: cold start to three replicas on two workers

One manager (the provider's daemon) and two worker hosts, all reachable over
TCP with TLS. The example pulls an image, initialises the swarm, joins both
workers, creates an overlay network and a secret, and runs three replicas that
only land on workers.

```terraform
terraform {
  required_providers {
    docker = {
      source = "JerryBalmer1/docker"
    }
  }
}

variable "manager_ip" { default = "10.0.0.10" }
variable "worker1_ip" { default = "10.0.0.11" }
variable "worker2_ip" { default = "10.0.0.12" }
variable "db_password" {
  type      = string
  sensitive = true
}

# The provider talks to the manager. Everything except the join goes here.
provider "docker" {
  host = "tcp://${var.manager_ip}:2376"

  tls {
    ca   = file("certs/manager/ca.pem")
    cert = file("certs/manager/cert.pem")
    key  = file("certs/manager/key.pem")
  }
}

# Layer 1: image. Pulled on the manager to resolve the digest; workers pull
# the same digest when their tasks start.
resource "docker_image" "web" {
  name         = "nginx:1.27-alpine"
  keep_locally = true
}

# Layer 3: swarm topology.
resource "docker_swarm_init" "this" {
  advertise_addr = var.manager_ip
}

resource "docker_swarm_node" "worker1" {
  host            = "tcp://${var.worker1_ip}:2376"
  join_token      = docker_swarm_init.this.worker_join_token
  manager_address = "${var.manager_ip}:2377"
  role            = "worker"
  labels          = { zone = "a" }

  tls {
    ca   = file("certs/worker1/ca.pem")
    cert = file("certs/worker1/cert.pem")
    key  = file("certs/worker1/key.pem")
  }
}

resource "docker_swarm_node" "worker2" {
  host            = "tcp://${var.worker2_ip}:2376"
  join_token      = docker_swarm_init.this.worker_join_token
  manager_address = "${var.manager_ip}:2377"
  role            = "worker"
  labels          = { zone = "b" }

  tls {
    ca   = file("certs/worker2/ca.pem")
    cert = file("certs/worker2/cert.pem")
    key  = file("certs/worker2/key.pem")
  }
}

# Layer 2 primitive used by the swarm: overlay networks need an initialised
# swarm, and no attribute says so, hence depends_on.
resource "docker_network" "app" {
  name       = "app"
  driver     = "overlay"
  attachable = true

  depends_on = [docker_swarm_init.this]
}

# Layer 4: workload. Secret data is base64. Rotate by bumping the suffix.
resource "docker_secret" "db_password" {
  name = "db_password_v1"
  data = base64encode(var.db_password)

  depends_on = [docker_swarm_init.this]

  lifecycle {
    create_before_destroy = true
  }
}

resource "docker_service" "web" {
  name     = "web"
  image    = docker_image.web.repo_digest
  mode     = "replicated"
  replicas = 3

  networks = [docker_network.app.id]

  placement {
    constraints = ["node.role==worker"]
    preferences = ["spread=node.labels.zone"]
  }

  secrets {
    secret_id   = docker_secret.db_password.id
    secret_name = docker_secret.db_password.name
    file_name   = "db_password" # mounted at /run/secrets/db_password
  }

  endpoint_spec {
    ports {
      target_port    = 80
      published_port = 8080
    }
  }

  update_config {
    parallelism    = 1
    delay          = "10s"
    order          = "start-first"
    failure_action = "rollback"
  }

  # Apply waits until all replicas are running (or fails after timeout).
  converge_config {
    timeout = "3m"
    delay   = "5s"
  }

  # The constraint only matches once workers have joined.
  depends_on = [docker_swarm_node.worker1, docker_swarm_node.worker2]
}
```

`terraform apply` creates, in order: image and swarm init (parallel), the two
joins, network and secret, then the service, and returns once three tasks run
on the workers. `terraform destroy` removes the service, secret and network,
makes both workers leave, and finally makes the manager leave the swarm.

## 10. Worked example 2: compose file to stack, seeded and scaled with actions

Migrating an existing `docker-compose.yml`. The compose file is input to a
one-off converter, never to the provider: after conversion you edit and commit
the generated `.tf`, and delete or archive the YAML. Needs Terraform >= 1.14
for the actions.

Step 1, the input (`docker-compose.yml`):

```yaml
services:
  db:
    image: postgres:16-alpine
    environment:
      POSTGRES_DB: shop
      POSTGRES_PASSWORD_FILE: /run/secrets/db_password
    secrets: [db_password]
    networks: [backend]
    deploy:
      placement:
        constraints: ["node.role==manager"]
  web:
    image: nginx:1.27-alpine
    ports: ["8080:80"]
    networks: [backend]
    deploy:
      replicas: 2
networks:
  backend: {}
secrets:
  db_password:
    file: ./db_password.txt
```

Step 2, convert it (from the provider repository; `make compose2stack
IN=docker-compose.yml OUT=stack.tf MODE=swarm` and `Invoke-Build
Compose2Stack -In docker-compose.yml -Out stack.tf -Mode swarm` run the same):

```shell
go run ./tools/compose2stack -in docker-compose.yml -out stack.tf -mode swarm
```

`-mode swarm` targets a Swarm `docker_stack`. Review the result for compose
keys that have no stack equivalent (build contexts, `depends_on` conditions,
host-only options) and fix those by hand. The generated file is
authoritative; it looks roughly like this:

```terraform
resource "docker_stack" "shop" {
  name = "shop" # objects are created as shop_<name>

  network {
    name = "backend"
  }

  secret {
    name = "db_password"
    data = filebase64("${path.module}/db_password.txt")
  }

  service {
    name     = "db"
    image    = "postgres:16-alpine"
    replicas = 1
    env = {
      POSTGRES_DB            = "shop"
      POSTGRES_PASSWORD_FILE = "/run/secrets/db_password"
    }
    networks = ["backend"]

    secrets {
      secret_id = "db_password"
      file_name = "db_password"
    }

    # On the manager, so docker_exec (which talks to the provider's daemon)
    # finds the task container.
    placement {
      constraints = ["node.role==manager"]
    }
  }

  service {
    name     = "web"
    image    = "nginx:1.27-alpine"
    replicas = 2
    networks = ["backend"]

    endpoint_spec {
      ports {
        target_port    = 80
        published_port = 8080
      }
    }
  }

  # Step 4: seed the database once, right after the stack is first created.
  lifecycle {
    action_trigger {
      events  = [after_create]
      actions = [action.docker_exec.seed_db]
    }
  }
}
```

Step 3, add the swarm and the actions next to it (`main.tf`):

```terraform
terraform {
  required_version = ">= 1.14"
  required_providers {
    docker = {
      source = "JerryBalmer1/docker"
    }
  }
}

provider "docker" {} # the swarm manager (DOCKER_HOST)

resource "docker_swarm_init" "this" {
  advertise_addr = "eth0"
}

# Runs inside a running task of shop_db on the provider's daemon.
action "docker_exec" "seed_db" {
  config {
    service = "shop_db"
    command = ["sh", "-c", "until pg_isready -U postgres; do sleep 1; done; psql -U postgres -d shop -c 'CREATE TABLE IF NOT EXISTS items (id serial PRIMARY KEY, name text)'"]
  }
}

# Not triggered by any resource: run it on demand.
action "docker_service_scale" "web_peak" {
  config {
    service  = "shop_web"
    replicas = 6
  }
}
```

Add `depends_on = [docker_swarm_init.this]` to the generated `docker_stack`
(nothing else orders it after the swarm exists).

Step 4, apply and operate:

```shell
terraform init
terraform apply                                          # swarm, then the stack; after_create runs action.docker_exec.seed_db
terraform apply -invoke=action.docker_service_scale.web_peak   # scale web to 6 now; nothing else changes
```

The scale action does not change configuration: the stack still says
`replicas = 2`, and the next plain `terraform apply` that updates the `web`
service puts it back to 2. To make a new size permanent, change `replicas` in
`stack.tf` instead. Re-running the seed later is
`terraform apply -invoke=action.docker_exec.seed_db`, which is why the SQL is
idempotent.

## 12. Translating compose

No compose YAML in the configuration: not as provider input, not as output,
not embedded in a heredoc. For a whole existing file use `tools/compose2stack`
once (worked example 2); when writing by hand, map each compose key to
resources:

| Compose | Swarm (`docker_service`) | Single host (`docker_container`) |
|---|---|---|
| `services.<name>` | one `docker_service` | one `docker_container` |
| `image` | `image` | `image` |
| `build` | `docker_image` with a `build` block, then `docker_registry_image` so workers can pull | `docker_image` with a `build` block; `image = docker_image.x.image_id` |
| `command` / `entrypoint` | `args` / `command` | `command` / `entrypoint` |
| `environment` | `env` map | `env` map |
| `ports: ["8080:80"]` | `endpoint_spec { ports { target_port = 80, published_port = 8080 } }` | `ports { internal = 80, external = 8080 }` |
| `volumes` (named) | `docker_volume` + `mounts { type = "volume", source, target }` | `docker_volume` + `mounts { type = "volume", source, target }` |
| `volumes` (bind) | `mounts { type = "bind", source, target }` | `mounts { type = "bind", source, target }` |
| `networks` | `docker_network` (`driver = "overlay"`) + `networks = [id]` | `docker_network` + `networks_advanced { name }` |
| `secrets` / `configs` | `docker_secret` / `docker_config` + `secrets {}` / `configs {}` blocks | not supported by the Engine for plain containers; use a bind or tmpfs mount |
| `deploy.replicas` / `deploy.mode` | `replicas` / `mode` | n/a |
| `deploy.placement` | `placement { constraints, preferences }` | n/a |
| `deploy.resources` (`cpus: "0.5"`, `memory: 512M`) | `resources { limits { nano_cpus = 500000000, memory_bytes = 536870912 } }` | `nano_cpus`, `memory` (bytes) |
| `deploy.update_config` / `rollback_config` | `update_config {}` / `rollback_config {}` | n/a |
| `deploy.restart_policy` / `restart` | `restart_policy {}` | `restart = "unless-stopped"` |
| `deploy.labels` / `labels` | `labels` / `container_labels` | `labels` |
| `healthcheck` | `healthcheck {}` | `healthcheck {}` |
| `logging` | `logging { driver, options }` | `log_driver`, `log_opts` |
| `depends_on` | Terraform references or `depends_on` (orders creation only, not readiness) | same |
| whole file / `docker stack deploy` | `docker_stack` with `service`, `network`, `volume`, `secret`, `config` blocks, or separate resources | separate resources |

Durations are Go duration strings (`"30s"`, `"5m"`). CPU is in nano CPUs and
memory in bytes. Prefer separate resources over `docker_stack` when objects
need their own lifecycle settings (for example `create_before_destroy` on a
rotated secret).
