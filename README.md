# terraform-provider-docker

A Terraform provider (registry address `JerryBalmer1/docker`) that manages the whole Docker chain, from image builds
to Swarm stacks, through the Docker Engine API. It never runs the `docker` CLI or the compose plugin: compose files
are parsed in-process, SSH is pure Go, and the only external program it can start is a docker credential helper, and
only when you set `allow_credential_helpers = true`.

the README disagrees, so a number here cannot go stale without the build saying so. The last column names the gate
that exercises what is counted.

How each number is produced:

- **Registered types** come from `internal/provider/registry_gen.go`, which `tools/registrygen` writes from
  `reference/inventory.json`. The short type lists are in the block below; every type, grouped by layer, is in
  [README_resources.md](README_resources.md) (generated from the provider schema).
- **Writable upstream fields** are every writable leaf field of the pinned Engine API swagger (request bodies and
  query parameters of the write operations a resource, action or ephemeral resource covers), of the compose-spec
  schema and of the bake target attributes. `tools/fieldcov` maps each one to a provider attribute (detected from the
  code and the schema) or records a reasoned skip or a partial in `reference/_gen/fieldmap.d/`. `FieldCoverage`
  fails on any gap.
- **Acceptance tests** run against a disposable Docker-in-Docker harness (a Swarm manager, workers, a TLS node and a
  containerd-store node) through `test/harness/Invoke-E2E.ps1`. Each skips cleanly when its environment is missing.
  The one that talks to Docker Desktop itself, `TestAccNpipeSmoke`, is opt-in (`TF_ACC_NPIPE=1`, Windows) and only
  touches `tfacc-npipe-*` objects.
- **Compose fixtures** are applied twice by `TestAccComposeParity`: once with the pinned `docker compose` release and
  once with `docker_compose`. The test then diffs the resulting containers, networks and volumes field by field.
- **Examples** are the `examples/` files the registry docs show. Each has a Pester test that applies it on the
  harness, requires an empty second plan, and destroys it.
- **Pairwise configs** come from `tools/pairwise`, which reads the live provider schema and the candidate values and
  Engine constraints in `reference/_gen/pairwise/<type>.json`, and writes the smallest set of configs it finds that
  covers every pair of values (fixed seed, so the set is the same on every run). `PairwiseTest` applies each one and
  compares terraform state with the daemon's inspect.

What is knowingly not done (skipped fields, partial features, deferred acceptance tests and example parts), each
with its reason and source, is listed in [reference/_gen/deferred.json](reference/_gen/deferred.json)
(`Invoke-Build DeferredReport`; `DeferredCheck` fails when it is stale).

`docker_buildx_builder` with `driver = "cloud"` (Docker Build Cloud) is implemented and unit-tested, but has not yet
been verified against the live Build Cloud service.

## Verify it yourself

You need Go, PowerShell 7 (`pwsh`), the InvokeBuild module (`Install-Module InvokeBuild -Scope CurrentUser`) and,
for the acceptance, example and pairwise gates, Docker Desktop or another Docker host that allows privileged
containers (it hosts the harness). From the repository root:

```powershell
Invoke-Build              # default task: build, vet, unit tests and every generated-file and coverage check
Invoke-Build PreRelease   # every pre-release gate in turn, then one table of results; nothing is tagged or pushed
```

`PreRelease` runs the gates listed in `$PreReleaseTasks` (`build/prerelease.tasks.ps1`): upstream drift, the
deferred list, the default task, gofmt, docs validation, stubs, kreuzwerker parity, the outputs contract, the
acceptance tests, the example tests, the pairwise tests and a local release snapshot. It keeps going past a failure
so one run shows every gate that needs work. `Invoke-Build ?` lists every task with a one-line synopsis.

## Quick start

```hcl
terraform {
  required_version = ">= 1.14.0"
  required_providers {
    docker = {
      source = "JerryBalmer1/docker"
    }
  }
}

# DOCKER_HOST, else the current Docker CLI context, else unix:///var/run/docker.sock.
provider "docker" {}

resource "docker_network" "app" {
  name = "app"
}

resource "docker_container" "web" {
  name  = "web"
  image = "nginx:1.27"

  ports {
    container_port = 80
    host_port      = 8080
  }

  networks = {
    (docker_network.app.name) = {}
  }
}
```

Actions and list resources need Terraform >= 1.14, write-only `*_wo` arguments >= 1.11, and ephemeral resources
>= 1.10. The provider configuration (hosts, TLS, SSH, contexts, registry credentials, owner labels, the Engine API
floor) is documented on the registry landing page, generated from
[templates/index.md.tmpl](templates/index.md.tmpl) into [docs/index.md](docs/index.md).

## Try it by hand

The scenarios in [test/__manual/](test/__manual/) are for a person at the keyboard: each is a `main.tf` and a
README saying what to look at after apply. They run on the same harness:

```powershell
Invoke-Build _List                                    # every scenario with its one-line description
Invoke-Build _Up                                      # start the harness (_Up -Swarm for the Swarm scenarios)
Invoke-Build _Init, _Plan, _Apply -Scenario <name>
Invoke-Build _Destroy -Scenario <name>
Invoke-Build _Down
```
