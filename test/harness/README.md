# End-to-end test harness

A throwaway Docker-in-Docker (`docker:29.9.3-dind`: Docker Engine 29.9.3,
Engine API 1.56, the version the provider targets) environment for the
provider's acceptance tests, on a user-defined bridge network `swarmnet`:

| Service | Host endpoint | Purpose |
|---|---|---|
| `manager` | `tcp://127.0.0.1:12375` | `DOCKER_HOST` for every test; swarm manager (the provider runs `docker_swarm_init` here, or `Invoke-E2E.ps1 -SwarmInit` does). |
| `worker1`, `worker2` | `tcp://127.0.0.1:12376`, `:12377` | Join targets for `docker_swarm_node`. |
| `worker3` | `tcp://127.0.0.1:12379` | NVIDIA-shaped worker with no GPU: daemon label `gpu=nvidia` (`engine.labels.gpu==nvidia`) and swarm generic resource `NVIDIA-GPU=GPU-0`, for placement tests. |
| `worker4` | `tcp://127.0.0.1:12381` | Standby worker: `Invoke-E2E.ps1 -SwarmInit` (`scripts/harness-swarm-init.*`) joins it right after `swarm init`, so the swarm pass always has a Ready worker (`docker_node`, `docker_node_promote` / `docker_node_demote`, `docker_node_drain`, global services). worker1-3 stay outside the swarm for the tests that join them. |
| `registry` | `http://127.0.0.1:12380` | `registry:2` with `REGISTRY_STORAGE_DELETE_ENABLED=true`, inside the manager's network namespace (see below). Seeded by `harness-up` with the Docker Hub images the tests use and the tfacc volume plugin. |
| `cdnode` | `tcp://127.0.0.1:12383` | Standalone daemon on the **containerd image store** (`TF_ACC_CONTAINERD_HOST`), not part of the swarm. The tests that need that store point `DOCKER_HOST` at it: `TestAccImageP6a_loadMultiPlatform` (multi-platform OCI archive through `docker_image_load`), `TestAccImageAttestations`, `TestAccBuildxP53_multiPlatform`, and `TestAccSwarmInitP6a_taskDefaults` (which inits and leaves a swarm on it). |
| `tlsnode` | `tcp://127.0.0.1:12378` | Standalone daemon that only accepts mutual TLS (`--tlsverify`), certificates generated by `harness-up`. Not part of the swarm. |
| `tlsregistry` | `https://127.0.0.1:12382` | `registry:2` over TLS with the harness server certificate (signed by the throwaway harness CA, so unverifiable for every client). For `TestAccRegistryImageDataInsecureSkipVerify`: the test seeds a tiny image over HTTPS itself and reads it with `data docker_registry_image`, failing with a certificate error when `insecure_skip_verify = false` and succeeding with `true`. No dind node uses it. |
| `mirror` | (not published) | `registry:2` in proxy mode for Docker Hub, every dind daemon's `--registry-mirror=http://mirror:5000`. |

### Engine version and image stores

Every dind node runs `docker:29.9.3-dind` (Engine 29.9.3, API 1.56; before
Pass 6a: `docker:28-dind`, Engine 28.5.2, API 1.51). Engine 29 puts a fresh
`/var/lib/docker` on the containerd image store by default, so both stores
are covered deliberately:

- `manager`, `worker1`-`worker4` and `tlsnode` run the **overlay2 graph
  driver**, set explicitly with `--storage-driver=overlay2
  --feature=containerd-snapshotter=false`. The swarm and almost every test
  use this store.
- `cdnode` runs the **containerd image store**
  (`--feature=containerd-snapshotter=true`, the Engine 29 default, made
  explicit).

`harness-up` prints the Engine version, API version and storage driver of the
manager and of `cdnode`, read from the daemons. It warns when the manager is
on the containerd store, and exports `TF_ACC_CONTAINERD_HOST` only when
`cdnode` really is on it (tests that need it skip otherwise).

### Docker Hub pull-through cache

Every `harness-up` starts fresh daemons, and every node pulls `nginx`,
`busybox` and `alpine` again. Anonymous Docker Hub pulls are rate-limited per
IP (100 per hour when measured), and back-to-back full runs exhausted that
(`toomanyrequests`). The `mirror` service caches Hub content in the
**external** volume `tfdocker-e2e-mirror-cache`, which `harness-up` creates
if missing and `harness-down` (`compose down -v`) leaves alone, so later runs
pull from the cache. Delete it with `docker volume rm
tfdocker-e2e-mirror-cache`. Registry data sources
(`DistributionInspect`) still ask Docker Hub directly.

All dind containers mount a tmpfs at `/run`: otherwise a stale containerd
pid file survives `docker compose restart` and the restarted daemon exits
("failed to save daemon pid to disk: process with PID N is still running").
Tests restart `worker2` and `tlsnode`.

`TestAccE2EImageToService` in `internal/provider/e2e_test.go` drives the
whole chain through the provider: image pull, swarm init, overlay network,
two worker joins, secret, and a 3-replica service spread across the workers.
`internal/provider/*_acc_p3_test.go` add the overlay data plane, registry
push/delete, TLS, autolock/locked manager, node import/adoption, GPU-shaped
placement and the remaining live checks.

The manager and workers listen on plain TCP **without TLS**, published on
`127.0.0.1` only. That is acceptable for a local, disposable harness and
nothing else.

### Seeded images: no Docker Hub in the tests

`harness-up` copies every image in `test/harness/seed-images.txt`
(`busybox:1.36`, `alpine:3.20`, `nginx:alpine`, `nginx:1.27-alpine`,
`docker/dockerfile:1`) into the harness registry: it pulls each on the
manager (through the mirror), pushes it as `manager:12380/<ref>`, removes
both local tags again (the manager starts with an empty image store), and
exports the references that worked as `TF_ACC_SEEDED_IMAGES`. The acceptance
tests run their Terraform configuration through `hAccTest`, and their Go-side
references (Dockerfiles, checks) through `hAccImage` / `hAccConfig`
(`internal/provider/h_harness_images_test.go`), which turn `busybox:1.36`
into `manager:12380/busybox:1.36`. That name works on the manager and on
every worker a Swarm task can land on. Without the harness, or for an image
that could not be seeded, the Docker Hub reference is used unchanged. Add an
image to `seed-images.txt` when a test starts using a new one.

Tests that exercise Docker Hub itself stay on Docker Hub, anonymously (no
credentials anywhere): `TestAccImageSearch` (`docker_image_search`, which the
daemon sends straight to index.docker.io; mirrors do not apply),
`TestAccRegistryTokenEphemeral` (Hub's token service) and
`TestAccP3RegistryImageDataSources` (a multi-arch index on Hub).
`harness-up` probes Hub search from the manager and exports
`TPD_ACC_INTERNET=1` when it answers, or `TF_ACC_SKIP_INTERNET=1` when it
does not, so those tests run online and skip, saying why, offline.
`TestAccComposeParity` pulls its own images through the mirror.

### Plugin fixtures (`tfaccplugin`)

`test/harness/tfaccplugin/main.go` is a test-only program (stdlib plus the
module's existing grpc / protobuf dependencies) that `harness-up` builds with
`GOOS=linux CGO_ENABLED=0 go build` into `test/harness/.plugins/` and packs as
two managed plugins (`config.json` + `rootfs/`):

- `volume/`: a no-op volume driver (`docker.volumedriver/1.0`, settable
  `DEBUG` env). `harness-up` creates it on the manager, pushes it as
  `127.0.0.1:12380/tfacc/noop-volume:1` and removes it again; it exports that
  reference as `TF_ACC_PLUGIN` (`TestAccPlugin_basic` installs, disables,
  re-configures and imports it) and the directory as `TF_ACC_PLUGIN_DIR`
  (`TestAccObjPluginCreatePush`).
- `csi/`: a controller-only CSI driver (`docker.csicontroller/1.0` +
  `docker.csinode/1.0`) answering the csi.v1 calls swarmkit makes to create,
  drain and delete a cluster volume (hand-encoded protobuf, so no CSI spec
  dependency). `harness-swarm-init` creates and enables it on the manager as
  `tfacc-csi` (`TF_ACC_CSI_PLUGIN`) for `TestAccObjClusterVolume`. It cannot
  publish a volume to a task.

Why these instead of a published plugin: both run as one static binary with
no kernel module, no FUSE device and no host mount, so they work inside dind
(`vieux/sshfs` needs `/dev/fuse` and `CAP_SYS_ADMIN` on the host kernel), and
they come from source, so no plugin registry or Docker Hub account is
involved. `TF_ACC_PLUGIN` may name any other plugin reference the daemon can
pull (`1` still means `vieux/sshfs:latest`).

### Registry address

`docker_registry_image` needs one name that works for the daemon (push,
`DistributionInspect`) and for the provider process (the `keep_remotely =
false` `DELETE /v2/<repo>/manifests/<digest>`). The registry therefore runs
with `network_mode: service:manager` and listens on 12380: `127.0.0.1:12380`
is the registry from the host and from the manager daemon alike, and
loopback registries are insecure (plain http) by default in dockerd. Every
dind node also has `--insecure-registry=manager:12380`, the name workers use
(`TF_ACC_REGISTRY_NODES`). Restarting the `manager` container detaches the
registry's network; recreate both with `harness-down` + `harness-up`.

### TLS material

`harness-up` writes a throwaway CA, a server certificate for `tlsnode`
(SAN `tlsnode`, `localhost`, `127.0.0.1`) and a client certificate into
`test/harness/tls/` (`ca.pem`, `cert.pem`, `key.pem`, `server-cert.pem`,
`server-key.pem`; RSA 2048, valid 30 days). The PowerShell script uses .NET
`CertificateRequest`, the bash script uses `openssl`. Existing files are
reused (a running `tlsnode` keeps the certificates it started with);
`tlsregistry` serves the same server certificate and key;
`harness-down` deletes the directory. It is git-ignored
(`test/harness/.gitignore`).

### Terraform CLI

terraform-plugin-testing v1.16 picks the CLI from `TF_ACC_TERRAFORM_PATH`
(exact binary), else installs `TF_ACC_TERRAFORM_VERSION` from
releases.hashicorp.com into a fresh temp directory **for every test**, else
uses `terraform` on `PATH`. The provider serves Terraform 1.14 features
(actions, list resources), so `harness-up` installs Terraform 1.14.9
(override with `HARNESS_TF_VERSION`) once into `test/harness/.bin/`
(SHA256-checked against the release's `SHA256SUMS`, kept by `harness-down`)
and exports both variables. If that download fails, only
`TF_ACC_TERRAFORM_VERSION` is exported and terraform-plugin-testing installs
it per test.

## Requirements

- A Docker host that allows `privileged` containers (Docker Desktop or Linux
  Docker Engine) with the `docker compose` v2 plugin.
- Outbound internet from the dind daemons on the first run (seeding pulls
  the images in `seed-images.txt` through the mirror, whose cache volume is
  kept) and from the host (`registry:2`, `docker:29.9.3-dind`, Terraform). The
  Docker Hub tests listed above need it on every run and skip without it.
- Free host ports 12375-12383.
- Go. For bash: `curl`, `unzip`, `openssl` (Git Bash ships all three).

## Run

From the repository root:

```powershell
pwsh -NoProfile -File test/harness/Invoke-E2E.ps1   # or: Invoke-Build E2E
```

This runs `harness-up`, the test, then `harness-down` (even if the test
fails), and exits with the test's status. `Invoke-Build TestAcc` runs every
acceptance test (plain pass, then `-SwarmInit` pass) the same way.

Manual sequence (useful to keep the harness up between runs):

```sh
bash test/harness/scripts/harness-up.sh
source test/harness/.env
# plain pass: manager outside any swarm (E2E, SwarmInit, container, image, registry, TLS)
TF_ACC=1 go test ./internal/provider/ -run TestAcc -count=1 -v -timeout 120m
SWARM='TestAcc(Service|Stack|Secret|DockerConfig|SwarmTokens|SwarmDataSources|Node_|Nodes_|NodeResource|SwarmNode|ComposeSwarm|ListSecret|P3SwarmList|ObjClusterVolume|Action(SwarmRotateTokens|NodeDrainActivate|ServiceScaleForceUpdateRollback|NodePromoteDemote|SwarmRotateCA|SwarmUnlockKey))'
TF_ACC=1 go test ./internal/provider/ -run TestAcc -skip "$SWARM" -count=1 -v -timeout 120m
# swarm pass: swarm init + worker4 joined + CSI plugin (service, stack, secret, config, nodes)
bash test/harness/scripts/harness-swarm-init.sh
TF_ACC=1 go test ./internal/provider/ -run "$SWARM" -count=1 -v -timeout 120m
bash test/harness/scripts/harness-down.sh
```

Both scripts can be run from any working directory.

## Windows (PowerShell 7)

The PowerShell scripts use the same compose file as the bash ones and
write the same `.env` (`export NAME=value`, LF line endings, forward-slash
paths, so bash `source test/harness/.env` still works):

| Script | Does |
|---|---|
| `test/harness/scripts/harness-up.ps1` | Fails fast with a clear message if `docker info` fails; generates `tls/` and installs Terraform into `.bin/`; `docker compose up -d --wait`; waits for every daemon (the TLS one with the client certificate) and the registry; writes `.env` and sets the same variables in the current session (`$env:DOCKER_HOST`, ...). |
| `test/harness/scripts/harness-swarm-init.ps1` | `docker swarm init` on the manager, joins worker4 and waits until it is Ready, enables the tfacc CSI plugin (bash twin: `harness-swarm-init.sh`). |
| `test/harness/scripts/harness-down.ps1` | `docker compose down -v --remove-orphans`, deletes `.env`, `tls/` and `.plugins/` and clears the variables (even if compose fails). |
| `test/harness/Invoke-E2E.ps1` | One-shot wrapper: up, then `TF_ACC=1` plus everything from `.env`, then (with `-SwarmInit`) `harness-swarm-init.ps1`, then `go test ./internal/provider/ -run <Run> [-skip <Skip>] -count=1 -v -timeout <Timeout>` from the repo root, with the full output tee'd to `-Log`, then down in a `finally` block. Exits with go test's exit code. |

`Invoke-E2E.ps1` parameters: `-Run` (default `TestAccE2E`), `-Skip` (go
test `-skip` regex, default none), `-Timeout` (default `30m`), `-Log`
(default `test/harness/last-e2e.log`, resolved against the repository root),
`-SwarmInit` (run `harness-swarm-init.ps1` first) and `-KeepUp` (leave the
harness running).
If the Docker daemon is not reachable it prints a one-line error and exits 1
before touching compose or `.env`.

From the repository root:

```powershell
# the image -> service chain (same as `Invoke-Build E2E`)
pwsh -NoProfile -File test/harness/Invoke-E2E.ps1

# every acceptance test, both passes: use Invoke-Build TestAcc, which passes
# $SwarmAccRegex (terraform-provider-docker.build.ps1) as -Skip of the plain
# pass and -Run of the swarm pass, so every swarm test runs exactly once:
#   Invoke-E2E.ps1 -Run TestAcc -Skip $SwarmAccRegex -Timeout 120m -Log test/harness/last-acc.log
#   Invoke-E2E.ps1 -SwarmInit -Run $SwarmAccRegex -Timeout 120m -Log test/harness/last-acc-swarm.log
Invoke-Build TestAcc
```

`Invoke-Build E2E` and `Invoke-Build TestAcc` at the repository root
call this script with those arguments.

Manual sequence (the harness stays up between runs):

```powershell
./test/harness/scripts/harness-up.ps1      # also sets $env:DOCKER_HOST etc.
$env:TF_ACC = '1'
go test ./internal/provider/ -run TestAccE2E -count=1 -v -timeout 30m
./test/harness/scripts/harness-down.ps1
```

Run the `.ps1` scripts in the current session (`./script.ps1` or `& ...`), not
with `pwsh -File`, if you want the `$env:` variables to stay set afterwards.

`DOCKER_HOST` and the variables it needs are set. Tests that run
`docker_swarm_init` themselves skip when the manager is already in a swarm;
tests that need a swarm manager skip when it is not (hence two passes; the
plain pass of `Invoke-Build TestAcc` leaves them out with `-skip`).

## Cleanup

`bash test/harness/scripts/harness-down.sh` (or `harness-down.ps1`) runs
`docker compose down -v` (containers, network, and the per-node
`/var/lib/docker` volumes) and deletes `.env`, `tls/` and `.plugins/`. If a run is
interrupted mid-test, running it is always safe. `test/harness/.bin/`
(the cached Terraform CLI) and the `tfdocker-e2e-mirror-cache` volume are
kept; delete them by hand to force fresh downloads.

## Compose CLI parity (`TestAccComposeParity`)

`internal/provider/compose_parity_acc_c_test.go` brings every compose
fixture (`internal/provider/testdata/compose_hash/*.yml` and the local
projects of `examples/resources/docker_compose/resource.tf`) up twice on the
manager daemon: once with the real `docker compose` CLI, once with
`docker_compose` (local mode). It then diffs the containers, networks and
volumes each created (image, command, env, mounts, ports, networks and
aliases, restart policy, driver options, every label including
`com.docker.compose.config-hash`). Any difference fails the test. Only
`com.docker.compose.version` and the provider's own `io.terraform.provider*`
labels are ignored.

- The provider never shells out; only this test runs the CLI (`os/exec` in a
  `_test.go` file), with `DOCKER_HOST` from `.env`.
- `harness-up` writes `TF_ACC_COMPOSE_CLI`, the path of the host's `docker`
  binary. The harness already needs the `docker compose` v2 plugin, so
  nothing new has to be installed. The test skips when `TF_ACC`,
  `DOCKER_HOST` or `TF_ACC_COMPOSE_CLI` is unset, or when
  `docker compose version` fails.
- Fixtures run one at a time under the fixture's own project name: the CLI
  project is brought up, recorded and removed (`down --volumes`), then the
  provider's.
- A fixture the CLI cannot bring up on the harness (for example a bind mount
  of a host path that the dind daemon does not have, or a missing build
  context) is skipped with the CLI's output, because there is nothing to
  compare against.
- It runs in the plain pass (no swarm needed).
